Session 8 — Run Your Own Model

Student handout · MKTG 6620 · October 19, 2026

Every model in this course so far has run on someone else's computer: you typed into ChatGPT or your coding agent, and a data center answered. Tonight the model runs on your laptop. You install llama.cpp, a free program that runs language models on ordinary computers, download two small models, and build a private AI assistant that works with the Wi-Fi off. Along the way you learn what is inside a model file, what each setting does, why the newest models are built the way they are, and why those designs make them hard to run yourself. The evening ends with a walkthrough of the final exam.

Case 3 is due Friday, October 23, at 11:59 p.m. Mountain. Tonight adds no graded work. The whole handout, every command, and the results we got are yours from the start, so you can check your screen against the page as you go.

Key concepts

Term Plain meaning
Self-hosting Running a model on hardware you control, instead of sending your text to a provider.
llama.cpp A free, open-source program that runs language models on laptops and servers: on the processor (CPU), on an Apple chip's graphics (Metal), or on a graphics card.
GGUF The single file llama.cpp loads: the model's weights plus its tokenizer and chat template.
Parameters (weights) The numbers a model learned in training. Qwen3.5-2B has about two billion.
Bits per weight How much storage each parameter takes. Fewer bits make a smaller file and usually a less accurate model.
Quantization Storing weights with fewer bits than they were trained with, such as 4 bits instead of 16.
Ternary weights Weights that are only −1, 0, or +1 (times a shared scale), about 1.6 bits of information each.
Token The unit a model reads and writes: a word, part of a word, or a symbol.
Context window How many tokens the model can hold at once: your messages, its replies, and any documents.
KV cache The model's notes on every token already in the context. It grows with the conversation.
Prompt processing and generation Reading the input (many tokens at once) and writing the reply (one token at a time).
Temperature, top-k, top-p, min-p Settings that decide how the next token is picked from the model's probabilities.
Thinking (reasoning) Writing out working before the answer. A thinking budget caps how many tokens it may spend.
Mixture of experts (MoE) A model split into many expert blocks, of which only a few run for each token.
Speculative decoding A cheap guesser drafts several tokens; the model checks them all in one step and keeps the ones it agrees with.
Multi-token prediction (MTP) Extra layers trained to guess the next few tokens, used as the model's own guesser.
K-quants, I-quants, imatrix Families of rounding recipes named in GGUF files (Q4_K_M, IQ2_M), and the importance matrix that tells the rounding which weights matter most.
Micro-batch (-ub) How many prompt tokens the chip processes at once.
Abliterated model A copy of a model with its refusal behaviour edited out of the weights.
n-gram A run of n tokens in a row, used to guess ahead or, in the newest models, as a lookup memory.
mmproj The vision add-on: a second file that turns an image into tokens the language model can read.
OpenAI-compatible API The request format most AI apps use. llama.cpp's server speaks it, so those apps can use your laptop's model.

1. Why run a model yourself?

The idea in one line. A model is a file of numbers plus a program that does arithmetic with them. If the file fits in your computer's memory, your computer can run it, and nothing you type leaves the machine.

Reason What it means The catch
Privacy Prompts, files, and replies never leave the laptop. Useful for client data, contracts, health records. You now secure the laptop and the files.
Cost No bill per question. A thousand questions cost electricity. The hardware isn't free, and someone has to maintain the setup.
Works offline On a plane, in a plant, behind a firewall. Updates and new models still need a download.
Control The file never changes. The same settings give the same answer next month. Hosted chat models change without notice. You have to choose and check the model yourself.
Quality — The models that fit on a laptop are far smaller than the ones behind ChatGPT or Claude. Section 10 explains why the gap is growing.

2. Install llama.cpp and download two models

You download three things: the llama.cpp programs (12 to 20 MB), and two models that share one design.

File What it is Size

qwen3.5-2b.gguf Qwen3.5-2B from Alibaba's Qwen team, stored at about 5 bits per weight (the Q4_K_M file from Unsloth), including its multi-token-prediction layer. Apache 2.0. 1.33 GB

3. Your first private conversation

Start a chat in the terminal:

./llama-b11714/llama-cli -m qwen3.5-2b.gguf -c 8192 --reasoning off

Wait for the > prompt, type a question, and press Enter. After each reply it prints its speed, such as [ Prompt: 14.0 t/s | Generation: 5.0 t/s ] (tokens per second). Ask it anything you like, then try one thing you'd never paste into a hosted chatbot, such as a made-up customer complaint with a name and an order number in it.

Now turn your Wi-Fi off and ask another question. It still answers. The whole model is in your laptop's memory; nothing is sent anywhere. Press Ctrl+C to leave the chat, and turn the Wi-Fi back on.

--reasoning off stops the model from thinking first, writing out its working before the answer. Section 9 measures what thinking buys and what it costs.

4. What's in a 1.33 GB file

A model file is mostly a very long list of numbers: the parameters, also called weights. llama.cpp prints what it loaded:

What llama.cpp printed Qwen3.5-2B (qwen3.5-2b.gguf) Bonsai 2 2B (bonsai-2b.gguf)
File size 1,268 MiB 521 MiB
Parameters 1.94 billion 1.88 billion
Bits per weight 5.43 2.28
Layers 24 24
Layers that keep notes on every token 6 6
Possible tokens (vocabulary) 248,320 248,320
Longest context it was trained for 262,144 tokens 262,144 tokens

Qwen3.5-2B counts slightly more parameters because its file also holds the multi-token-prediction layer (section 10).

The file's size follows from two numbers:

File size ≈ parameters × bits per weight ÷ 8 (bytes). The model's design sets the parameters; the file format sets the bits.

For Qwen3.5-2B: 1.94 billion parameters × 5.43 bits ÷ 8 ≈ 1.3 GB. For Bonsai 2 2B: 1.88 billion × 2.28 bits ÷ 8 ≈ 0.54 GB. The same design, stored with fewer bits, makes a file less than half the size.

Quantization: fewer bits per weight

Most models are released with 16 bits per weight. Storing each weight with fewer bits is called quantization. The usual way rounds a finished model's weights to a coarser grid, and the smaller the grid, the more the model's answers drift. File names tell you the format:

Name in the file Bits per weight (about) What it means
BF16, F16 16 The weights as trained.
Q8_0 8.5 8 bits per weight plus a scale per block of 32. Close to the original.
Q4_K_M 4.5–5 The popular default: 4-bit blocks, with more bits kept for the most sensitive layers.
Q2_K, IQ2_M 2.5–3 Rounded hard. Ordinary models lose noticeable quality here.
Q2_0 (Bonsai) 2.3 Ternary weights, −1, 0, or +1, two bits each plus scales. Works only because the model was trained to use those three values.

PrismML reports that its ternary Bonsai 2 models keep most of the original model's benchmark scores. That is the company's own measurement; section 8 lets you check the 2B model on a few questions of your own.

Deeper: one model, twenty-one files

Open the Hugging Face page our Qwen file came from and you find 21 versions of the same model. Every one holds the same 1.94 billion parameters; they differ only in how each weight was rounded.

Family File names How it rounds When to use it
Legacy (2023) Q4_0, Q4_1, Q5_0, Q8_0 Each block of 32 weights shares one scale (and, in the _1 types, an offset). Simple, and fast on every chip. Q8_0 as a near-perfect copy; Q4_0 for older or unusual chips.
K-quants (2023) Q2_K to Q6_K, with _S, _M, _L Blocks inside super-blocks of 256, with the scales themselves rounded. The last letter says how many sensitive layers get extra bits: small, medium, large. The everyday choice: Q4_K_M, or Q5_K_M and Q6_K if memory allows.
I-quants (2024) IQ1_S to IQ4_XS, IQ4_NL Rounds small groups of weights to the nearest entry in a fixed codebook, so fewer bits lose less. Made with an importance matrix (next screen). Slower on some processors. Below about 4 bits, where K-quants fall apart.
Unsloth Dynamic UD-Q4_K_XL, UD-IQ2_M, … Chooses the type layer by layer, after measuring which layers suffer most, and keeps those at higher precision. When you want the most quality per gigabyte.

Two things the names hide, seen in tonight's own file:

  • Q4_K_M is a recipe, not a promise of 4 bits. Our file mixes five types: 113 tensors at Q4_K, 27 at Q6_K, 18 at Q5_K, 1 at Q8_0, and 176 small ones left at 32 bits. That's why llama.cpp reported 5.43 bits per weight.
  • Small models shrink less. The vocabulary table alone, 248,320 tokens × 2,048 numbers, is 0.51 billion parameters, a quarter of the model, and it is kept at 6 bits. So the 3-bit file (Q3_K_S, 1.07 GB) is only about 20% smaller than tonight's.

Deeper: who makes the files, and how to choose

The Qwen team released the model in 16 bits. Almost everyone runs a copy that someone else rounded, and who rounded it matters as much as the format.

Who What they publish
The model's makers Some labs publish their own GGUF files. Fewest choices; the most trusted source.
ggml-org llama.cpp's own organization: standard files for popular models, often with the vision and MTP parts as separate files.
Unsloth Many sizes, including their Dynamic (UD) files, tuned on more than 1.5 million tokens of hand-picked chat text; MTP versions, like tonight's. Dynamic 3.0, launched in August with Qwen3.8, claims better accuracy at the same size than every other maker; that is Unsloth's own measurement.
bartowski, mradermacher Community uploaders with very wide sets of K- and I-quants, most made with an importance matrix.

The importance matrix (imatrix). Before rounding, run some sample text through the model and record which weights matter most for its outputs; then round those more carefully. Unsloth's is in the same folder as a 1.9 MB file, imatrix_unsloth.gguf_file. The sample text matters: rounding tuned on English chat can hurt code or other languages a little more.

How to choose a file. (1) Take the largest file that fits in memory with room left for the KV cache (section 5). (2) Start at Q4_K_M or UD-Q4_K_XL; go up to Q5 or Q6 if there's room; Q8_0 is close to the original. (3) Below 4 bits, prefer I-quant or UD files. (4) At the same memory, a bigger model at 4 bits usually beats a smaller model at 8 bits. (5) Check it on your own questions, as in section 8.

Other formats you'll meet: MLX (Apple's own engine, in 4-bit and 8-bit folders); GPTQ and AWQ (graphics cards, used by vLLM); FP8, and the 4-bit floating-point formats MXFP4 and NVFP4 on newer NVIDIA chips (OpenAI released its gpt-oss models in MXFP4). And QAT files, like Bonsai, were trained to be rounded, rather than rounded afterwards.

5. Memory: the file plus the conversation

Loading a model takes more memory than the file. llama.cpp also keeps a KV cache, the model's notes on every token in the conversation, so it doesn't have to reread everything to write the next word. The cache grows with the context length you allow with -c.

At 4,096 tokens of context Qwen3.5-2B's cache is 48 MiB; at 32,768 tokens, 384 MiB; at its full 262,144 tokens, 3,072 MiB, which is 3 GiB and more than twice the weights. On top of that llama.cpp reserves about half a gigabyte of scratch space for the arithmetic. Only 6 of the model's 24 layers keep notes on every token; the other 18 keep a fixed-size summary, 19 MiB in all, however long the conversation (section 10, jump 2). That's why tonight's commands set -c 8192: plenty for a chat, with a cache under 100 MiB.

Rule of thumb. You need memory for the whole file, plus the cache for the context you allow, plus some scratch space. A laptop that can't hold all three either refuses to load the model or slows to a crawl.

Deeper: the cache can be rounded too

The KV cache is numbers, just like the weights, so it too can be stored with fewer bits. By default llama.cpp keeps each note in 16 bits (f16). Two settings change that:

./llama-b11714/llama-server -m qwen3.5-2b.gguf -c 262144 -ctk q8_0 -ctv q8_0 -lv 4

-ctk sets the type for the keys and -ctv for the values; -lv 4 makes the server print its memory details. Search the terminal (Cmd+F or Ctrl+F) for llama_kv_cache: size, then stop the server and start it again without -ctk q8_0 -ctv q8_0 to compare. Rounding the values needs flash attention: llama.cpp turns it on by itself ("enabling flash_attn since it is required for quantized V cache"), and refuses to start if you force it off with -fa off. At this full context the server needs 3 to 5 GB, so skip it on an 8 GB laptop.

  • 8 bits (q8_0) halves the cache, with almost no change in the answers. It is the common choice.
  • 4 bits (q4_0) cuts it to under a third, but every step of a long conversation now reads slightly blurred notes. llama.cpp's developers suggest keeping the keys at least as precise as the values, for example -ctk q8_0 -ctv q4_0. How much it hurts depends on the model; test it.
  • When it matters. At tonight's -c 8192 the cache is under 100 MiB, so leave it alone. An older 32-billion-parameter design that keeps notes in all 64 of its layers (Qwen2.5-32B) needs 8 GiB of cache for 32,768 tokens at 16 bits, and 4.25 GiB at q8_0. There it decides whether the model fits.

6. Speed: reading is fast, writing is slow

Measure your laptop. llama-bench times two things: reading a 512-token prompt (pp512, prompt processing) and writing 128 tokens (tg128, token generation).

./llama-b11714/llama-bench -m qwen3.5-2b.gguf -m bonsai-2b.gguf

It takes a minute or two and prints a table. The t/s column is tokens per second. Write your two tg128 numbers and your laptop model on the board.

Our run: 16 cores of a server processor, no GPU Reading, pp512 (tokens/s) Writing, tg128 (tokens/s)
Qwen3.5-2B (qwen3.5-2b.gguf) 156.3 32.7
Bonsai 2 2B (bonsai-2b.gguf) 95.4 16.6

Two lessons are in that table:

  • Reading is much faster than writing. Reading a prompt handles all its tokens together, so the chip works on many at once. Writing produces one token at a time, and each token needs every weight read from memory once. So writing speed depends mostly on how fast the chip can read its memory (its memory bandwidth) divided by the size of the weights, as long as the arithmetic keeps up. Qwen3.5-2B wrote 32.7 tokens per second on 16 cores of our server processor, with no GPU.
  • A smaller file isn't always faster. Bonsai's file is less than half the size of Qwen's, yet it wrote at about half Qwen's speed on our server. Its new number format needs extra arithmetic for every weight, and the fast code for ordinary Intel and AMD processors only arrived on October 13 (section 10, jump 5). On your laptop it may come out differently; that's what the board is for.

The board will show a wide spread. Apple's Pro and Max chips read memory several times faster than the base chips, and a Windows laptop running on its processor alone is usually slower than a Mac using its GPU. llama.cpp picks sensible settings for your machine; the ones you may meet later are -t (processor threads), -ngl (how many layers go to the GPU; on a Mac, all of them), and -fa (a faster way to compute attention, on by default where it helps).

Deeper: -b and -ub, how much of the prompt is read at once

llama.cpp doesn't push a long prompt through the model in one go. It cuts it up twice:

Setting Default What it is
-b (batch) 2,048 The most prompt tokens llama.cpp hands the model in one call.
-ub (micro-batch) 512 The most tokens the chip actually computes at once. Each batch is split into micro-batches.

Section 6 said reading is fast because one fetch of the weights serves many prompt tokens at once. -ub is how many. Measure it on your laptop:

./llama-b11714/llama-bench -m qwen3.5-2b.gguf -p 2048 -n 0 -ub 32,128,512,2048

On our 16-core server the default, -ub 512, read fastest: 129 tokens per second, against 67 at -ub 8 and 113 at -ub 2048. Larger was slower here, and the scratch space grew with it, by about 1 MiB for every token in the micro-batch: llama.cpp reserves room to score all 248,320 possible next tokens for each one. At -ub 2048 that is 2,068 MiB, more than the model. A graphics card has far more arithmetic to spare, so there larger micro-batches keep paying off for longer.

When to change them. On a graphics card with long prompts (documents, code), raise both, for example -b 4096 -ub 4096, if memory allows. It matters most for mixture-of-experts models whose experts are kept in ordinary memory (--n-cpu-moe), because each micro-batch copies the experts to the graphics card once. Short of memory, lower -ub to shrink the scratch space. Writing speed doesn't change: writing is one token at a time.

7. The settings, and what they mean

Now run the model as a server. This is the build you'll keep using tonight:

./llama-b11714/llama-server -m qwen3.5-2b.gguf -c 8192 -np 1 --port 8080

When the terminal says listening on http://127.0.0.1:8080, open http://127.0.0.1:8080 in your browser. That chat page is served by your own laptop. Leave this terminal window open; closing it stops the server.

Part of the command What it sets
-m qwen3.5-2b.gguf Which model file to load.
-c 8192 The context window: at most 8,192 tokens of conversation. More costs memory (section 5).
-np 1 One conversation at a time. Each extra slot gets its own context.
--port 8080 The address on your laptop: 127.0.0.1 means this computer only, and 8080 is the door number.

In the chat page, the lightbulb next to the model's name sets thinking for each message. Set it to Off for now; section 9 turns it on. Under each reply the page shows how many tokens it wrote and how many per second.

How the next word is chosen

At every step the model gives each of its 248,320 possible tokens a probability. We asked Qwen3.5-2B "What is the best national park in Utah? Reply with the park's name only." Here are its probabilities for the first token of its answer:

The sampling settings decide how one token is picked from that list:

Setting llama.cpp default What it does
temperature 0.8 Reshapes the probabilities. Below 1 sharpens them toward the favorite; 0 always picks the favorite; above 1 flattens them, so unlikely words win more often.
top_k 40 Keep only the k most likely tokens.
top_p 0.95 Keep the smallest set of top tokens whose probabilities add up to p.
min_p 0.05 Drop any token less than this fraction as likely as the favorite.
presence_penalty, repeat_penalty 0, 1.0 (off) Make tokens that already appeared less likely, to stop loops.
seed random The random draw. The same seed and settings give the same reply on the same machine.
max_tokens (-n) no limit Stop after this many tokens.

Qwen's model card recommends temperature 1.0, top_p 1.0, top_k 20, and presence penalty 2.0 for text without thinking. In the chat page, open Settings (the gear on the left), then Sampling & Penalties, to change any of them for your next message.

Try it: one prompt, three temperatures

In Settings → Sampling & Penalties set Top K to 0, Top P to 1, and Min P to 0, so that only temperature changes. Then ask this three times at each temperature, each time in a new chat. The page draws a new random seed for every message; we fixed seeds 1, 2, and 3 so you can compare:

Suggest one name for a new coffee shop in Salt Lake City. Reply with the name only.

Temperature Seed 1 Seed 2 Seed 3
0.0 Salt Lake Mountain Brew Salt Lake Mountain Brew Salt Lake Mountain Brew
0.7 Mountain Peak Roastery The Salt Lake Mountain Roast Salty Roast
1.5 Cle употреблять York The建行 keskust lofty zoomn和国家 hall china amer … Volume Wiki menyinger chill decor write L把EO Lounge

At temperature 0 the favorite wins every time, so the seed doesn't matter. At 0.7 each seed gives a different, mostly sensible name. At 1.5, with nothing cutting off the unlikely tokens, rare tokens win often enough to turn the reply into nonsense. That is what top_k, top_p, and min_p are for: they drop the long tail before the draw. Set them back to the defaults (40, 0.95, and 0.05) when you're done.

8. Is a 2-billion-parameter model good enough? Check it.

You wouldn't trust an analysis without checking it, and the same goes for a model. In the chat page set the lightbulb to Off and Temperature to 0, so each answer is the model's favorite, and paste these eight questions one at a time, in a new chat for each. Then stop the server, start it again with -m bonsai-2b.gguf in place of -m qwen3.5-2b.gguf, and ask them again.

  1. From this email, what date is the meeting? Reply with the date only. Email: "Hi team, we're moving the vendor review from Thursday to Tuesday, October 27, at 10 a.m., same room. Dana"
  2. Classify this support ticket as billing, shipping, technical, or other. Reply with one word. Ticket: "I was charged twice for my order last week and need one of the charges refunded."
  3. What is 17% of 2,340? Reply with the number only.
  4. A store sells 340 units a week at $12.50 each. Next week the price rises 8% and units sold fall 5%. What is next week's revenue in dollars? Reply with the number only.
  5. Which planet is closest to the Sun? Reply with one word.
  6. Who was the dean of the University of Utah's David Eccles School of Business in 2020? Reply with the name only.
  7. Return only a JSON object with the keys "product" and "quantity" for this order: "Please send three boxes of printer paper."
  8. How many times does the letter r appear in the word strawberry? Reply with the number only.

What we got

Question Correct answer Qwen3.5-2B Bonsai 2 2B
1. Meeting date from an email october 27 Right: October 27 Right: October 27
2. Ticket category billing Right: billing Right: Billing
3. 17% of 2,340 397.8 Wrong: 3178 Right: 29.98 2340 * 0.17 = 299.8 Wait, let me recal … 397.8 Answer: 397.8 </think> 397.8
4. Next week’s revenue 4360.5 Wrong: 1283 Wrong: 12.50 * 340 * (1 + 0.08) * (1 - 0.05) = 12.50 * 340 * 1.08 * 0.95 = 4000.00 4000
5. Planet closest to the Sun mercury Right: Mercury Right: Mercury
6. Eccles dean in 2020 taylor randall Wrong: David Eccles Wrong: David Eccles was the dean of the University … David Eccles School of Business in 2020.
7. JSON for an order quantity 3 Right: { "product": "printer paper", "quantity": 3 } Right: { "product": "printer paper", "quantity": 3 }
8. r’s in “strawberry” 3 Wrong: 4 Wrong: 5

Qwen3.5-2B got 4 of the 8 right and Bonsai 2 2B got 5. Both pulled the date and the ticket category out of the text, knew the planet, and wrote the JSON. Both named "David Eccles", the man the school is named after, as its 2020 dean: a confident, plausible invention. Taylor Randall was dean from 2009 until he became the university's president in 2021. Both missed the revenue and the r's in "strawberry". Qwen got 17% of 2,340 badly wrong; Bonsai got it right only because, though told not to think, it wrote out its working anyway. Section 9 comes back to that.

These are the usual failures of small models: arithmetic, facts they never stored, and anything that needs the letters inside a token. Pulling facts out of text you supply, sorting it into categories, and formatting it are what they do well. Now paste the same eight questions into ChatGPT EDU and compare. Which of these tasks would you hand to a 1.3 GB model on a laptop, and which not?

Deeper: "abliterated" and "uncensored" models

Search Hugging Face for almost any popular model and you'll find copies named "abliterated" or "uncensored": the same model with its refusals taken out. NPR counted more than 6,000 abliterated models there in May 2026, up from about 600 in 2024.

Uncensored (retrained) Abliterated (edited)
How it's made Trained again on examples with the refusals removed. Eric Hartford's 2023 essay "Uncensored Models" made the idea popular. In 2024 researchers showed that refusing is controlled largely by one direction in the model's internal numbers (Arditi and others, NeurIPS 2024). Abliteration subtracts that direction from the weights. No training.
Effort Training on graphics cards Minutes to hours on one graphics card; tools such as Heretic search for the edit that removes refusals while changing everything else least
What else changes Style and quality can shift Benchmark scores drop a little, and behaviour shifts in ways nobody aimed at: in one July 2026 study, abliterated models gave more optimistic stock calls

The business view:

  • Why people want them. Official models sometimes refuse legitimate work: security testing, medical and legal questions, fiction, content moderation. Over-refusal is a real cost.
  • Why to be careful. You remove a layer of safety you may be relying on. The model will now answer requests your company's policy forbids, and your company owns what it says. The licence still applies.
  • Uncensored isn't more truthful. Taking out refusals adds no knowledge; it would still invent the Eccles dean.
  • Unknown uploader, unknown edits. A stranger's copy can differ from the original in ways you can't see by reading the file.
  • A better first step. Try a clear system prompt or a vendor's enterprise settings first. If you do use an edited model, put your own checks around it (filters, logs, human review) and write down why.

Watch (optional).

  • Andy Arditi, “Refusal in LLMs Is Mediated by a Single Direction”, 28 minutes: the paper's first author on how the refusal direction was found.

9. Thinking: better answers, at a price

The idea in one line. A thinking model writes out its working before it answers. More working often means more right answers, but every thinking token costs the same time, memory, and, on a hosted model, money as any other token.

Hosted products sell the same trade-off under other names: the thinking modes in ChatGPT, the "reasoning effort" setting in AI companies' APIs, and Claude's extended thinking. On your laptop you can see exactly what it costs. The lightbulb in the chat page sets it for each message:

Lightbulb What the page asks the model for
Off No thinking: answer straight away.
Low Think for at most 512 tokens, then answer.
Medium Think for at most 2,048 tokens.
High Think for at most 8,192 tokens.
Max Think as long as it likes.
Default Whatever the model does when not told. Qwen's model card says its 2B model doesn't think unless asked, but with this file in llama.cpp it does: our test question took 431 tokens. Bonsai 2 also thinks by default.

Try it

Set Temperature back to its default, 0.8. Ask these three questions from section 8 at Off, then at Low, each in a new chat. Click the thinking block above a reply to read the working. For each, note: right or wrong, tokens written, and seconds. Leave Medium, High, and Max alone tonight: a 2B model on a laptop can think for minutes, and sometimes never stops.

What is 17% of 2,340? Reply with the number only.

A store sells 340 units a week at $12.50 each. Next week the price rises 8% and units sold fall 5%. What is next week's revenue in dollars? Reply with the number only.

How many times does the letter r appear in the word strawberry? Reply with the number only.

What we got

All eight questions from section 8, asked three times each (seeds 1, 2, and 3) at Off and at Low, with llama.cpp's default sampling, on Qwen3.5-2B:

Lightbulb Right answers Tokens written (median) Time (median) Slowest reply
Off 12 of 24 5 0.2 s 10 s
Low (512 thinking tokens at most) 18 of 24 518 18.7 s 19 s

With thinking off, Qwen3.5-2B got 12 of 24 right, writing a median of 5 tokens in under a quarter of a second. With a 512-token budget it got 18 of 24, writing about 100 times as many tokens and taking 18.7 seconds per answer on our server. Look at where the gain came from:

  • Thinking fixed the arithmetic and the counting. The percentage went from 0 of 3 to 3 of 3, and the r's in "strawberry" from 0 of 3 to 3 of 3. The model worked them out step by step.
  • Thinking can't supply a missing fact. The dean stayed at 0 of 3: no amount of working produces a name the model never stored.
  • A budget too small can make things worse. The revenue question needs more than 512 tokens of working. The budget cut the thinking off mid-calculation, and two of the three replies gave the new price, $13.50, instead of the revenue. 15 of the 24 Low replies ran into the budget.

More thinking: the larger budgets

Medium, High, and Max raise the budget to 2,048 tokens, 8,192 tokens, and no limit. We didn't measure them, for the reason above, but the pattern is well known from the large thinking models:

  • Accuracy rises with the budget, then levels off. Hard multi-step problems keep improving with more thinking for a while; easy questions don't improve at all, because the model already knew the answer.
  • Cost rises in step with the tokens. Every thinking token takes the same time to write, holds the same space in the KV cache, and, on a hosted model, is billed like the answer.
  • Small models get less out of it. A 2B model can wander, repeat itself, or argue itself out of a right answer. Large models make better use of long thinking.
  • The wait is the customer's. A reply that takes a minute is fine for a monthly report and useless for a live chat.

The trade-off, in business terms

Off Low Medium, High, Max
Right answers on our eight questions, three tries each 12 of 24 18 of 24 Not measured
Tokens written per question (median) 5 518 (about 100 times as many) Up to 2,048, 8,192, or no limit
Time per question on our server (median) 0.2 s 18.7 s Minutes on a laptop; a small model may never stop

A decision rule for your team. Turn thinking on where a wrong answer is expensive and the task has steps (arithmetic, planning, code). Leave it off where the answer is in the text you supply (extraction, classification, formatting) or where a person is waiting. Then check the rule on your own questions, as you did tonight.

10. Five jumps in how models are built, and why each makes self-hosting harder

Large language models have changed shape since 2023. The open models from DeepSeek, Qwen, and others publish their designs; the closed models behind ChatGPT, Claude, and Gemini publish less but face the same costs. Five changes matter most. Each one makes models cheaper and faster to serve in a data center, and each one makes them harder to run yourself.

Qwen3.5-2B, on your laptop DeepSeek-V4.1-Flash, released September 10
Parameters stored 1.94 billion 552 billion
Parameters used for each token it writes All of them About 16 billion
Published weights 1.33 GB (our 5-bit file) 510 GB
Long-term cache per token 12 KiB (48 MiB for 4,096 tokens) 890 bytes
Longest context 262,144 tokens 1,000,000 tokens
Runs in llama.cpp tonight Yes No: too big for a laptop, and not yet supported

Jump 1. Mixture of experts: huge models that use a small part per token
What changed Instead of one block of weights that every token passes through, each layer holds many "experts", and a small router picks a few for each token. DeepSeek-V4.1-Flash (September 10, 2026) has 552 billion parameters. Each layer has 384 routed experts and 1 shared one, and 6 routed experts run per token, so about 16 billion parameters work on each token it writes. Qwen3.5-35B-A3B: 35 billion parameters, 3 billion active.
Why it matters Each token costs about as much arithmetic as a 16-billion-parameter model, but the model has the knowledge of a far bigger one. Providers can serve it cheaply.
Why it's hard to self-host Speed depends on the active parameters, but memory depends on all of them, because the next token may need any expert. 552 billion parameters at 4 bits is about 276 GB; a well-equipped laptop has 16 to 32 GB. Workarounds keep experts in ordinary memory or stream them from the SSD, and they are slow. A llama.cpp proposal to stream experts from disk has been open since July 4.

Jump 2. Cheaper memory for long conversations
What changed Long context made the KV cache the main memory cost. Newer designs shrink it. Qwen3.5 keeps per-token notes in only 6 of its 24 layers; the other 18 use linear attention (Gated DeltaNet), which keeps a fixed-size summary however long the conversation gets. DeepSeek-V4.1-Flash shares its cache across layers, attends only to selected past tokens, and stores the cache at 4 bits: 890 bytes per token, about a quarter of its predecessor's, with contexts up to a million tokens.
Why it matters Agents read whole codebases, long documents, and pages of tool output. A smaller cache means longer contexts and more users per machine.
Why it's hard to self-host Every new kind of attention is new arithmetic that someone must write, and make fast, separately for each kind of chip: Intel and AMD processors, Apple's GPU, NVIDIA's, and the rest. llama.cpp added a new operation just for DeepSeek's sparse attention. Features that rewind or reuse a conversation are harder when part of the memory is a running summary.

You measured this jump in section 5: Qwen3.5's cache at its full 262,144-token context is 3 GiB; with all 24 layers keeping notes it would be four times that.

Jump 3. Built-in guessers: multi-token prediction
What changed Models now ship with a small extra part that guesses the next few tokens, so the big model can check several at once (section 11 explains how). DeepSeek-V3 (December 2024) trained a multi-token prediction (MTP) layer; its guess for the second token was accepted 85% to 90% of the time, for about 1.8 times as many tokens per second. Qwen3.5-2B, the model on your laptop, has one. DeepSeek-V4.1-Flash uses a separate three-block guesser that drafts five positions at once.
Why it matters The same answers, faster, at no loss of quality.
Why it's hard to self-host Each kind of guesser is its own piece of software. llama.cpp b11714 lists eleven settings for --spec-type, and the option names changed between versions this year. The speed-up needs spare arithmetic capacity, which a data-center GPU serving many users has and a laptop may not. Section 11 measures it.

Jump 4. Reading and writing split apart
What changed DeepSeek-V4.1-Flash is a causal encoder–decoder: its 40 layers are split into a 20-layer encoder and a 20-layer decoder. Reading the prompt runs mostly the encoder half, about 8 billion active parameters per token; writing each new token runs the whole model, about 16 billion. DeepSeek says this nearly halves the cost of reading.
Why it matters Agents' work is mostly reading: files, search results, tool output. Making reading cheap cuts the cost of agents.
Why it's hard to self-host It is a new model layout, so every program that runs models has to add it. The llama.cpp pull request to support it was opened on September 10, the day the model came out, and is still open on October 18: 2,090 new lines of code in 23 files. Some of its savings, such as keeping parts of the cache on an SSD, assume data-center storage.

Jump 5. Trained for very few bits
What changed Instead of rounding a finished model, train it to work with ternary or 1-bit weights. PrismML's Bonsai 2 27B fits in about 6 GB; the 2B model on your laptop is 0.55 GB.
Why it matters Capable models on laptops and phones, and far less memory traffic per token.
Why it's hard to self-host New number formats need new code for every chip. In llama.cpp, Apple GPU support for Q2_0 arrived July 14, NVIDIA support July 30, PrismML's Bonsai 2 runtime October 11, and the fast path for ordinary Intel and AMD processors October 13. Bonsai's 1.83-bit PTQ1_0 files still run only in PrismML's own copy of llama.cpp. PrismML says Windows hasn't been checked for its small models.

The pattern

Jump Who it helps most What it costs a self-hoster
Mixture of experts Providers serving many users Memory for every expert
Cheaper long-context memory Agents with long inputs New arithmetic for every chip
Built-in guessers (MTP) Fast replies on busy GPUs Separate software per guesser; small gains without spare capacity
Encoder–decoder split Input-heavy agent work A new model layout to support; data-center storage tricks
Trained low-bit weights Laptops and phones New number formats; forks until support lands

The newest models arrive designed for data centers, and open-source software catches up weeks or months later, one chip at a time. When a vendor says a model is "open weights", ask two questions before planning to host it: how much memory do all its weights need, and does the software you'd run it on support its layout yet?

11. Speculative decoding, live

The idea in one line. Writing one token needs a full pass through the model, but checking several proposed tokens costs about the same as writing one. So guess a few cheaply, check them in one pass, and keep the ones the model agrees with.

Guesser Where the guesses come from llama.cpp setting
Multi-token prediction The model's own extra layer, trained to guess ahead --spec-type draft-mtp
n-gram Copying what followed the same few words earlier in the conversation. Free, and good at edits, rewrites, and quoting a document --spec-type ngram-simple or ngram-mod
Draft model A smaller model of the same family -md small.gguf --spec-type draft-simple

With temperature 0 the reply should be the same with or without guessing; only the speed changes. In practice a near-tie can occasionally flip a word, as our results show.

Try it

Stop the server with Ctrl+C. Start it again with the MTP guesser on:

In the chat page, keep the lightbulb at Off, set Temperature to 0, and ask both prompts below; the page shows tokens per second under each reply. Then restart with --spec-type ngram-simple --spec-draft-n-max 64 in place of --spec-type draft-mtp, and once more with no --spec-type at all, and ask the same two prompts.

If a customer orders before 3 p.m. on Monday, the order ships the same day. Returns are accepted at the front desk during opening hours, and gift cards can be used for any item in the store. The staff meeting is on Monday at 8:30 a.m., before the doors open, and everyone should bring their weekly sales sheet. Parking is free for customers in the lot behind the building.

Deeper: what MTP is, exactly

An ordinary model reads the text and predicts the next token. A multi-token-prediction (MTP) block is one extra layer that predicts the token after that.

  • In training. The block is trained together with the model (Meta 2024; DeepSeek-V3, December 2024). Predicting two tokens ahead gives the model more to learn from in every sentence and pushes it to plan. Meta's 13-billion-parameter models solved 12% more coding problems on one test and 17% more on another; DeepSeek also reported better scores.
  • In use. The block becomes a built-in guesser: it drafts the next few tokens, and the full model checks them in one pass, as in section 11. It guesses well because it starts from the model's own internal state, not from scratch.
  • You can see it in tonight's file. Qwen3.5-2B has 24 layers plus a 25th block, blk.24, whose parts are named nextn ("next n"): 61 million parameters, 42 MB, 3% of the file. Without --spec-type draft-mtp, llama.cpp skips it and says so in the log: model has unused tensor blk.24.nextn.eh_proj.weight … ignoring.
  • Why "MTP" is in the file's name. Until May 2026 the usual conversion to GGUF threw this block away, and llama.cpp could only use it from May 16. Unsloth converted Qwen3.5 again to keep it. Newer repositories, such as Qwen3.8's, ship the block as its own small file, mtp-….gguf, next to the model.
  • Relatives. Medusa adds several small heads, each guessing one position; EAGLE trains a small separate layer that reads the model's internal state; DeepSeek-V4.1-Flash dropped its MTP block for a separate three-stage drafter that proposes five tokens at once. All of them guess cheaply from work the big model has already done.

Watch (optional).

  • bycloud, “Why would anyone let LLMs predict 4 tokens at once? Multi-Token Prediction Explained”, 11 minutes: Meta's paper and DeepSeek-V3's MTP.

Deeper: n-grams, from guessing to memory

An n-gram is a run of n tokens in a row: "the back room" is a 3-gram. The idea is older than neural networks, and in 2026 it came back in two places.

1. As a free guesser: what you ran in section 11. ngram-simple looks at the last few tokens; if the same tokens appeared earlier in the conversation, it proposes what followed them then.

2. As a memory inside the model. DeepSeek's Engram (paper, January 2026) and Qwen's Qwen3.8-Flash-Next (August 26, billed as a preview of Qwen4) add a huge lookup table to the model itself. At each position the model turns the last 2 to 4 tokens into a row number, fetches the vector stored in that row, and blends it into its thinking.

DeepSeek-V4.1-Flash (September 10) Qwen3.8-Flash-Next (August 26)
Where Two tables, at layers 1 and 14 One table, at layer 2
What is looked up 2-, 3-, and 4-grams 2- and 3-grams
How big About 384 million rows per table 51 billion parameters

Why both labs do it:

  • Remembering is cheap; computing is expensive. Names, phrases, and facts that always follow the same words ("Salt Lake" → "City") can be looked up instead of worked out by many layers of arithmetic, which frees those layers for reasoning. DeepSeek calls it "a new axis of sparsity", next to mixture of experts.
  • A lookup isn't arithmetic. It costs the same however big the table is. Because the row depends only on the words already there, the table can sit in the computer's ordinary memory and be fetched ahead of time, instead of filling the graphics card.
  • For self-hosters it cuts both ways. Tens or hundreds of billions of parameters that need no fast chip, but still need memory, and one more new layout for llama.cpp to support (jump 4).

  • Jia-Bin Huang, “DeepSeek Gave LLMs a Real Memory (It's Not RAG)”, 28 minutes; from 6:27: lookup, hashing, and how the model decides when to trust the table.

Deeper: the vision add-on (mmproj)

Look again at the folder our model came from: next to the 21 model files are three called mmproj. Qwen3.5 was trained on text and images together from the start, and so was Qwen3.8-27B (August 2026), which also reads video. The language model you've used all evening is one part; the mmproj file is the part that sees.

Why it's a separate file What that means
It's a different network A vision encoder with 24 layers of its own, about a third of a billion parameters for this model. llama.cpp runs it with separate code.
It's optional No images, no need to load it, and 0.67 GB stays free. Text-only models, like Qwen3.8's 2.4-trillion-parameter flagship, have none.
It stays at 16 bits It is small, and rounding hurts it more, so makers rarely shrink it: you choose F16, BF16, or F32.
It belongs to one model It works only with the language model it was trained with.

How an image gets in: the encoder cuts it into squares of 16 × 16 pixels and turns each square into a list of numbers; the projector merges each 2 × 2 group of squares into one token the language model can read. A bigger image means more tokens, more memory, and a longer wait.
