How tonight's search works

The idea in one line. A model turns each passage, and each question, into a list of numbers. Texts that mean similar things get similar lists, so search returns the passages whose lists sit closest to the question's.

Key concepts

Term Plain meaning
Embedding (vector) A list of numbers a model makes from a piece of text. Texts with similar meaning get similar lists, even when they share few words.
Dimensions How many numbers are in each list: 384 for BGE-small, 1,024 for full Qwen3-0.6B, 256 for our shortened Qwen3.
Cosine similarity How closely two vectors point the same way. Higher means closer in meaning; 1 is the most similar possible.
Cosine distance 1 minus the cosine similarity. Databases report this one, so lower means closer. Neither number is the chance that a passage is right.
Metadata filter A rule on ordinary fields applied before ranking. Ours keeps only current policies for the brand named on the request.
Vector database A database that stores each passage's text, fields, and vector, and can find the vectors nearest a question. We use LanceDB, and PostgreSQL with pgvector on the projector.
Catalog The plain record of what the library holds: IDs, text, brand, status, version, and embedding settings. We keep it in SQLite.

2. Choose an embedding model and a number of dimensions

An embedding model turns text into a vector. Search then takes three steps. Save one vector per passage. Turn each incoming question into a vector with the same model and compatible settings. Return the passages whose vectors are nearest. Search only finds passages. Drafting an answer from them is a separate job for a language model, which comes in Session 7.

What “nearby” means

Picture each vector as an arrow. BGE-small's arrows have 384 numbers each. Cosine similarity measures how closely two arrows point the same way. Every saved vector in this package has length 1 (the metadata says “L2 unit length”), so cosine similarity is simply the dot product: multiply the matching numbers and add them up. Databases report cosine distance, which is 1 minus the similarity.

Meaning-based search at work

Validation question CLASS-validation-07 comes from a Canyon customer. The intended passage is Canyon's Damaged delivery policy. The two share only “the” and “and.” Our keyword search ranks Store pickup first because it shares three words (“the,” “and,” “are”), and Damaged delivery misses its top three. BGE-small puts Damaged delivery first:

Customer question · Canyon · CLASS-validation-07 Intended passage · Canyon · Damaged delivery
“The box arrived crushed and the contents are broken. What evidence should I save?” “Report transit damage within 4 days of receipt. Keep the packaging and send photographs of the parcel and item.”

The only words the two share are in bold: “the” and “and.”

Canyon passage (BGE-small) Cosine similarity Cosine distance
Damaged delivery (intended) 0.655644 0.344356
Warranty 0.573254 0.426746
Store pickup 0.545986 0.454014

The model learned from many examples that “crushed,” “broken,” and “evidence” travel with “transit damage,” “packaging,” and “photographs.” To reproduce the first row yourself, start Python from the package folder with .venv active (type python) and paste in:

import json, numpy as np
meta = json.load(open("data/bge_small.json"))
v = np.load("data/bge_small.npz")
q = v["queries"][meta["query_ids"].index("CLASS-validation-07")]
d = v["documents"][meta["document_ids"].index("CLASS-2-07")]
sim = float(q @ d)       # dot product = cosine similarity for length-1 vectors
print(len(q), round(sim, 6), round(1 - sim, 6))   # 384 0.655644 0.344356

A similarity ranks; reading decides

Notice that the winner above scores only 0.66. Across the eight validation questions, the intended passages score between 0.63 and 0.70 under BGE-small. Use a similarity to rank passages, and read the passage to judge it.

The models in this package

Model or family Output dimensions Practical use and input convention
all-MiniLM-L6-v2 384 Small English starting point; saved class vectors are included.
BGE small / base / large English v1.5 384 / 768 / 1,024 Small is included. For this question-to-passage task, put Represent this sentence for searching relevant passages: in front of each question and leave documents as they are.
BGE-M3 1,024 for dense vectors Multilingual. It can also produce other kinds of output, but our saved example uses only its standard single vector (dense vectors only), without the BGE-English question prefix.
Qwen3-Embedding-0.6B / 4B / 8B 1,024 / 2,560 / 4,096 at full size Takes an instruction on the question side. We use 0.6B, saved at full size and in a supported shortened 256-dimensional version.

Three numbers that are easy to mix up, using Qwen3-Embedding-0.6B:

0.6B parameters: the model's size, about 0.6 billion internal numbers it learned in training
1,024 dimensions: how many numbers it saves for each text
32K tokens: its context limit, how much text it can read at once

Tokens are word pieces. BGE-M3's documented limit is 8,192 tokens, and Qwen3-Embedding's is 32K. Our longest input is 44 tokens, far inside every model's limit as we ran them: MiniLM reads at most 256 tokens, and we capped the others at 512. Nothing was cut off. A big context limit is still no reason to embed a whole manual as one item. A service rep needs a passage short enough to read and quote.

The dimensions don't have names

No single number in the list stands for a business field like “returns” or “price,” so you can't pick fields by deleting positions. Qwen3 was trained to allow shorter outputs. Our 256-dimensional version keeps the first 256 numbers, then rescales each shortened vector back to length 1 (renormalizes it), for questions and documents alike. Only shorten a model whose documentation says it supports this, and rerun the search comparison afterward.

Watch (optional).

  • Weaviate, “Matryoshka Representation Learning (MRL) for ML tasks and vector compression”, under 3 minutes: why a model can be trained so the first numbers carry the most meaning.

Same length doesn't mean compatible

MiniLM and BGE-small both produce 384 numbers, and BGE-M3 and Qwen3-0.6B both produce 1,024. Each model arranges meaning its own way, though. Search one model's passage vectors with another model's question vector and you get results that look plausible but are nonsense, and nothing crashes to warn you. So record the model ID, revision, dimensions, input conventions, normalization, and text version next to the vectors. When results look odd later, that record shows whether questions and passages went through the same recipe. If any of these settings change, build a new collection from scratch.

Calculate the storage consequence

Vectors are usually stored as float32, which uses 4 bytes per number, so raw vector storage is passages × dimensions × 4 bytes.

These are back-of-the-envelope figures, not measured database sizes. A real system also stores text, metadata, any search index, working memory, the model itself, and backups. Cutting dimensions shrinks what you store, but it doesn't necessarily make encoding cheaper. Our Qwen 256 vectors come from the same full Qwen run, trimmed afterward.

How hard is this test?

After the filter, each question chooses among only the 8 current passages for its brand. A random pick would put the intended passage first 1 time in 8 (12.5%) and would include it in three picks 3 times in 8 (37.5%). Compare found-in-three with that floor as well as with keyword. A real library with hundreds of passages per brand is a much harder search.

recall3 in the output files is the share of questions whose intended passage shows up in the top three (recall1 is the share where it comes first). The uncertainty ranges are already in outputs/validation_metrics.csv, so you don't have to compute anything. Eight questions is a small sample, so even a perfect 8/8 leaves a wide 95% range for the true success rate, approximately 67.6–100% (ci_low, ci_high). Each embedding method beats keyword on recall3 by 25 percentage points (8/8 versus 6/8), but the 95% range for that gap runs from 0 to 62.5 points (delta_low, delta_high). In plain terms, the data fit anything from no advantage to a large one. These ranges also assume our questions are a fair sample of real ones. We wrote them ourselves, so they may not sound like BRG's actual customers, and these 30 policies can't tell you which model is best in general.

4. Build a LanceDB table and query it again

LanceDB's local library keeps a whole table in an ordinary folder, so there's no database server to set up. Each row holds a passage's ID, text, metadata (brand, status, version), and vector. With only 30 passages, LanceDB can compare the question with every row, which is called an exact scan. Very large libraries add an approximate index for speed, but vector search works without one. LanceDB documents vector search and distance choices here.

5. Use SQLite for the catalog; back it up safely

SQLite is a database that runs inside your own program. Python ships with it (sqlite3), and there's no separate server to install or look after. The script uses it for the catalog: each document's ID, text, status, and version, plus the embedding settings. SQLite can store vectors as raw bytes, but it has no built-in way to find the nearest ones quickly. That takes an extension or a different tool, and in this lab LanceDB does the vector search.

Ask your agent to open the catalog, practice/store/catalog.sqlite, and run:

SELECT brand, status, COUNT(*) AS passages
FROM documents GROUP BY brand, status ORDER BY brand, status;
SELECT doc_id, title FROM documents
WHERE brand = 'Alta' AND status = 'current';

Each brand has eight current and two archived passages. SQL answers exact questions such as “which current Alta records exist?” Vector search answers a fuzzier one: “which passage is closest in meaning to this wording?” Our search uses both. The filter narrows the list, and the vectors rank what's left.

Ask SQL Ask the vectors
Which current Alta records exist? Which passage is closest in meaning to this wording?
Exact rules on fields: brand, status, version A ranking by cosine distance
Same answer every time, no judgment needed A short list a person still reads

Why a live database doesn't belong on a network or synced drive

NFS (Network File System) makes a folder on another machine look like a folder on yours, and CHPC's shared storage works this way. SQLite protects its file by locking it during a write and by confirming each write has reached the disk. Network file systems don't always handle locking the way a local disk does, and every small step has to cross the network. SQLite's own network guidance recommends a client/server database for this situation. A test that happened to work once doesn't prove the setup will hold up when several people use it at once.

The script turns on SQLite's WAL (write-ahead log) mode. New changes go first into a side file ending in -wal, and programs sharing the database coordinate through shared memory that exists only on one machine. So WAL mode can't let clients on different machines share a database over a network file system, and switching journal modes won't make shaky NFS locking reliable. SQLite WAL documentation.

Our practice rule: keep the active database on a local disk, use one machine for this exercise, and store only a finished backup on shared storage. On a laptop, the same risk comes from folders that OneDrive, iCloud Drive, or Dropbox sync, because they copy files in the background. Keep live databases out of them. Don't try to prove the point by corrupting a database on purpose. If a service has to be used from several machines, give it a database server that manages its own files and have everyone send queries to that server, as PostgreSQL does in section 6.

6. Try PostgreSQL through psql

PostgreSQL is the database server. psql is its command-line client. A server is how many people share one database. It is the only program that touches the database files. Everyone else connects to it and sends SQL, so nobody opens those files over NFS. An administrator still sets up where the server keeps its files and how they're backed up. PostgreSQL's psql documentation.

The pgvector extension adds vector columns and vector search to PostgreSQL. It has to be installed and switched on in the server itself. Installing a Python package on your laptop doesn't do that. Our tested example stores vectors in a vector(384) column and sorts by <=>, pgvector's cosine-distance operator, smallest distance first. PostgreSQL without the extension understands neither.

The search at the end of postgres_practice.sql, laid out to read:

SELECT doc_id, title,
       embedding <=> (SELECT embedding FROM queries
                      WHERE query_id = 'CLASS-dev-01') AS cosine_distance
FROM policies
WHERE brand = 'Alta' AND status = 'current'   -- the filter
ORDER BY cosine_distance, doc_id               -- nearest first
LIMIT 3;                                       -- the top three

The file creates its own schema (a separately named area inside the database) and deletes nothing. That schema name is fixed, though, so the supplied file runs only once per database; a second run stops with “schema already exists.” If a run stops with an error, type ROLLBACK; before anything else. Until you do, PostgreSQL refuses every other command in that session with “current transaction is aborted,” and the psql prompt shows =!#.

To run the SQL in your own sandbox, generate a fresh file from the package folder and start psql from that folder so \i can find it:

It prints the new schema name, which includes the time of export, so every export gets a different one. Check the index limits before you pick a big model

At larger scale, check two limits: how long a vector the column can hold, and how long a vector the index (the structure that makes search fast) can handle. In the pgvector version we tested, its two fast index types, HNSW and IVFFlat, work on vector columns up to 2,000 dimensions and on halfvec columns (2 bytes per number) up to 4,000. Full-size Qwen 4B vectors (2,560 dimensions) are too long to index as vector, and full-size Qwen 8B vectors (4,096) are too long even for halfvec, so either model needs a deliberate storage and index choice. In class we use small exact scans, so there's no index to tune.

Beyond today

Tonight's library is tiny and tidy on purpose. A real deployment meets these choices next.

Topic What it is Why it matters for a team like BRG's
Keyword (BM25) and hybrid search BM25 is the standard keyword score in search tools: it gives more weight to rare words and discounts long passages. Hybrid search runs keyword and vector search together and merges the two lists. Exact strings such as order numbers, SKUs, and form names favor keyword search; paraphrases favor vectors. Our questions were written as paraphrases, which flatters vector search.
Reranking Retrieve a longer list, then let a second model score each question–passage pair and pick the final few. Often sharpens the top results, at extra cost and delay per question.
Chunking long documents Splitting manuals into passages before embedding. Ours arrived pre-cut, one rule each. Split at headings or numbered clauses, and store title, brand, status, and date with every passage. Changing the split rule means a new collection.
Hosted embedding API or local model A provider embeds your text for you, or you run an open model such as BGE or Qwen yourself. With an API, policy text and customer questions leave your network and you pay per amount of text. The provider can also retire a model, which means re-embedding every passage. A local model keeps data in-house and lets you pin a revision, but you supply the hardware and upkeep.
Exact scan or approximate index An exact scan compares the question with every vector. An approximate nearest-neighbor index, such as HNSW or IVFFlat, checks only a promising subset. The index is much faster on millions of passages but can miss the true nearest one, so check found-in-three with and without it.
